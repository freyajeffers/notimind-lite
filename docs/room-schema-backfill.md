# Room Schema Backfill — Obstacles and Realistic Path Forward

This document records an honest accounting of why historical Room schemas
(`1.json` .. `17.json`) cannot be generated by a naive checkout-build-copy
strategy, and what would actually be required to backfill them.

The investigation was prompted by the `@Ignore`d scaffolded test in
[`tier1_feature/MigrationTest.migration_17_to_18_runsSuccessfullyAndPreservesNotificationsTable`](../app/src/test/java/com/notimind/lite/tier1_feature/MigrationTest.kt).
The scaffold is correct, compilable, and matches the official Room migration
testing recipe — but it cannot run because `MigrationTestHelper.createDatabase(17)`
requires `app/src/test/resources/com.jeffers.notimindlite.data.local.AppDatabase/17.json`
as an Android asset, and that JSON does not exist in source control.

## Why a naive backfill fails

### 1. Initial build was v6, not v1

`git show b5e921c:app/src/main/java/com/jeffers/notimindlite/data/local/AppDatabase.kt`
shows `@Database(entities = [NotificationEntity::class], version = 6, exportSchema = false)`.

This means **migrations `1_2` through `5_6` have no source schema to start from**.
They are defensive-only code added retroactively to support hypothetical older
forks of the codebase. They can never be exercised by `MigrationTestHelper` no
matter what backfill work is done.

### 2. Cross-version type dependencies break cherry-pick

Each commit's `AppDatabase.kt` references entities that didn't exist at that
commit:

| Entity                | Introduced at version | Introducing commit |
|-----------------------|-----------------------|--------------------|
| `NotificationEntity`  | v6                    | `b5e921c` (initial) |
| `AppEntity`           | v10                   | `8ff1c04`           |
| `NotificationFtsEntity` | v14                 | `8e90e85`           |
| `BackupRecord`        | v16                   | `e292424`           |

Attempting to check out a historical `AppDatabase.kt` (e.g., v17) against
current sources produces:

```
e: [ksp] [MissingType]: Element 'com.jeffers.notimindlite.data.local.AppDatabase'
   references a type that is not present
```

The KSP error does not name the missing type — debugging it requires removing
entities from `@Database(...)` one at a time until the build succeeds.

A full-commit checkout (the entire `b5e921c` tree) fails for different reasons:
the historical commits predate `gradle/wrapper/`, `gradle/libs.versions.toml`,
and several KSP/Room/AGP versions that evolved separately. Building at
historical commits requires either (a) maintaining a historical build
infrastructure or (b) bringing modern wrapper + version catalog into a
historical commit, neither of which is sustainable.

### 3. `identityHash` is Room-internal

Even if the schema entities/indices/columns could be reverse-engineered from
`18.json` plus the SQL of `MIGRATION_N_N+1`, the `identityHash` field in
each schema JSON is computed by Room's internal normalization logic and is
not exposed via any public API. A synthetic schema with a wrong
`identityHash` will fail `MigrationTestHelper.validateMigration` immediately
with:

```
java.lang.IllegalStateException: Room cannot verify the data integrity.
   Looks like you've changed schema but forgot to update the version number.
   You can bump the version number in the @Database annotation.
```

## What an actual backfill would require

A custom **synthetic schema generator** that uses Room's internal APIs
(`DatabaseConfiguration`, `RoomDatabase.Builder`, reflective access to
`IdentityHash` computation) to emit a valid `<version>.json` for any
historical version given the current entity class definitions. Estimated
scope:

- **Code:** 200–300 lines of Kotlin
- **Prerequisite:** reading Room 2.7.0 source to identify the public-or-
  accessible-by-reflection API that produces the schema JSON. Possibilities:
  `androidx.room.util.SchemaDump`, `androidx.room.RoomOpenHelper` via
  reflection on private fields, or constructing a `DatabaseConfiguration` and
  serializing it.
- **Output:** a one-shot CLI / Gradle task that emits `1.json` .. `17.json`.
- **Verification:** each generated JSON should be re-validated by Room's
  own `MigrationTestHelper.validateMigration` against the next version's JSON
  using the corresponding `MIGRATION_N_N+1`.

This is real engineering work (likely 1–3 focused sessions). It is NOT a
"git checkout historical, build, copy" operation.

## Current state (verified at session end)

- `app/schemas/com.jeffers.notimindlite.data.local.AppDatabase/18.json` is the
  only schema in source control.
- `tier1_feature/MigrationTest.smoke_notificationRoundTripSucceedsAtCurrentSchema`
  is green; exercises Room end-to-end at v18.
- `tier1_feature/MigrationTest.migration_17_to_18_*` is `@Ignore`d pending
  either (a) the synthetic schema generator above or (b) hand-construction
  of just `17.json` (the only migration that could conceivably be enabled
  without historical backfill, since it's adjacent to the existing v18).
- Master branch is clean and in sync with `origin/master`.

## Decision

Backfill deferred. The scaffold stays in place so future work can pick it up
when the engineering bandwidth is available.
