# Master Phased Implementation Plan: Local Filesystem RAG MCP Server

## Consolidated Architectural & Operational Roadmap

### 1. Executive Overview & Reconciliation Context

This master implementation plan reconciles the high-level operational vision of an offline-first, low-overhead search daemon with the existing, mature filesystem-rag-mcp-main codebase. Rather than discarding the prototype or attempting to build a narrow, disconnected note indexer from scratch, this plan leverages the repository's modular architecture (featuring ~25 specialized modules, full-text search, vector indexing, query caching, multi-format conversion, and codebase intelligence) and systematically layers in the unfulfilled operational requirements:

- Domain & Workload Specialization: Introducing profile-driven configurations that seamlessly support dedicated personal notes indexing alongside full-codebase intelligence.

- Hardware-Conscious Inference Tuning: Formally pinning ONNX Runtime and FastEmbed thread pools to exploit host CPU topology (specifically the AMD Ryzen 5 5600XT 6-core/12-thread architecture) while maintaining portable, configurable fallbacks.

- Daemonization & Service Orchestration: Establishing production-grade systemd user service and timer definitions on Arch Linux for autonomous, self-healing background synchronization.

- Retrieval Accuracy & Regression Benchmarking: Implementing a standardized 25-query evaluation harness tracking MRR@5 and Hit@1 across lexical, semantic, hybrid, and reranked pipelines.

- Automated Database Maintenance Runbooks: Deploying scheduled compaction, FTS5 segment optimization, and incremental vacuuming to ensure sustained sub-75ms latency over multi-year operational lifecycles.

### Phase 1: Workload Profiles & Domain Specialization

#### Objective & Scope

Bridge the gap between the codebase's general-purpose filesystem capabilities and the user's requirement for a dedicated, zero-overhead personal notes vault indexer without fragmenting the package architecture.

#### Architectural Components & Responsibilities

- Configuration Profile System: Extend the existing configuration module to support distinct operational profiles:

- Personal Notes Profile: Defaults to ~/.local/share/notes, strictly targets Markdown extensions (*.md, *.markdown), and enables aggressive editor artifact filtering.

- General Codebase Profile: Preserves existing multi-format ingestion, code symbol extraction, git tracking, and directory tree inspection across arbitrary software repositories.

- Editor Artifact Exclusion Filters: Standardize file-path filters within the watcher and indexing subsystems to ignore temporary files commonly generated by Vim, Neovim, and other terminal text editors:

- Vim swap files (e.g., .*.swp, .*.swo, .*.swx).

- Vim persistent undo files (e.g., .*.un~).

- Editor backup files (e.g., *~, *.tmp, .goutputstream-*).

- Markdown AST Breadcrumb Optimization: Ensure that when the personal notes profile is active, the chunking pipeline preserves hierarchical heading paths (from H1 through H6) in chunk metadata, providing structural context for localized note snippets.

- CLI Profile Overrides: Update the CLI entry point to accept profile flags, enabling instant switching between personal note indexing and project-level codebase scanning.

- Environment Doctor Enhancements: Update the diagnostics module (doctor.py) to validate path existence, directory readability, and filter rules for the configured profile.

#### Acceptance & Verification Criteria

- Activating the notes profile restricts ingestion to Markdown documents in ~/.local/share/notes.

- Vim swap, undo, and backup files produce zero file watcher events or database write transactions.

- General codebase operations continue to pass all existing format-conversion and symbol-extraction tests without regression.

- Diagnostic checks accurately report the active profile, target directory status, and index statistics.

### Phase 2: Hardware-Conscious Inference & Adaptive Thread Pinning

#### Objective & Scope

Optimize machine learning inference pipelines to maximize embedding and reranking throughput on the host processor (AMD Ryzen 5 5600XT) without causing UI micro-stutters, thread starvation, or thermal throttling.

#### Architectural Components & Responsibilities

- Hardware Profile Abstraction: Implement an adaptive hardware configuration layer in the configuration module:

- Host Profile (AMD Ryzen 5 5600XT): Explicitly sets ONNX Runtime parameters to intra_op_num_threads = 6 (matching physical Zen 3 cores) and inter_op_num_threads = 1.

- Adaptive Fallback Profile: Inspects available physical CPU cores on non-target systems and automatically bounds thread pools to prevent scheduler oversaturation.

- Thread Pool Isolation: Isolate ONNX Runtime sessions between the bi-encoder embedding model (bge-small-en-v1.5) and the cross-encoder reranker (bge-reranker-base) to ensure parallel executions do not compete for compute resources.

- Startup Graph Warm-Up: Execute a synthetic warm-up inference pass during service initialization to compile dynamic execution kernels and populate CPU caches before servicing interactive queries.

- Three-Stage Retrieval Funnel Calibration:

- Stage 1 (Broad Recall): Retrieve top 50 candidates from FTS5 lexical matching and top 50 candidates from dense vector similarity, merging them via Reciprocal Rank Fusion (RRF) with constant k = 60.

- Stage 2 (Rerank Pool Cut): Slice the top 20 candidates from the RRF output for the cross-encoder inference pass.

- Stage 3 (Final Projection): Sort cross-encoder results by calibrated sigmoid relevance scores, returning the top 5 highest-scoring chunks to the client.

- Query Cache Integration: Ensure the existing query caching module intercepts repeated or identical query vectors, bypassing embedding computation and cross-encoder evaluation entirely.

#### Acceptance & Verification Criteria

- ONNX Runtime inference initializes with verified thread allocations (6 intra-op, 1 inter-op on host).

- Startup warm-up successfully eliminates initial query latency spikes.

- Retrieval funnels adhere strictly to the 50/50 recall, 20 rerank cut, and 5 final projection boundaries.

- Repeated search queries return from cache in sub-millisecond time.

- System monitor checks verify that background indexing and interactive search do not cause desktop stuttering or thread deadlocks.

### Phase 3: Service Daemonization & Systemd Lifecycle Management

#### Objective & Scope

Transition the existing inotify file watcher into a resilient, autonomous background system daemon supervised by systemd user services on Arch Linux, decoupled from interactive terminal sessions.

#### Architectural Components & Responsibilities

- Systemd User Service Unit: Define the service unit file at ~/.config/systemd/user/mcp-rag-watcher.service:

- Unit Configuration: Meaningful description, documentation pointers, and dependency ordering requiring default user targets.

- Execution Profile: Points directly to the isolated Python virtual environment binary running the background watcher module.

- Environment Configuration: Injects active profile, notes directory path, database location, and unbuffered logging flags.

- Restart Policy: Configured with Restart = on-failure and RestartSec = 5s for self-healing resiliency.

- Process Sandboxing: Directives for user-space protection (e.g., restricted temporary directory, memory limits).

- Journald Structured Logging: Route service standard output and error streams directly to systemd journald with standardized log severity levels (INFO, WARNING, ERROR).

- Persistent User Lingering: Document and support user account lingering configuration (loginctl enable-linger) to ensure continuous watcher execution when the user is logged out or working remotely.

- CLI Lifecycle Management: Provide convenience CLI commands in cli.py (e.g., install-service, start-service, stop-service, service-status) that interface directly with systemctl --user.

- Inter-Process Concurrency Governance: Verify that the background watcher service (writer) and the on-demand FastMCP stdio server (reader/writer) operate concurrently over the shared SQLite database without lock conflicts, relying on SQLite WAL mode and the 5000 ms busy timeout.

#### Acceptance & Verification Criteria

- Systemd user service installs, starts, stops, and reloads without syntax or permission errors.

- Simulating process termination (e.g., kill -9) triggers automatic recovery within 5 seconds.

- Live service logs are viewable via journalctl --user -u mcp-rag-watcher.service.

- The FastMCP server connects via stdio, queries the database, and serves results while the watcher daemon actively syncs changes in the background.

### Phase 4: Retrieval Quality Benchmarking & Regression Gates

#### Objective & Scope

Establish an automated evaluation harness and quantitative regression gates to guarantee search precision and verify that architectural updates do not degrade retrieval accuracy or violate latency budgets.

#### Architectural Components & Responsibilities

- Curated Evaluation Dataset: Construct a version-controlled ground-truth benchmark comprising at least 25 representative technical queries mapped to verified document and chunk identifiers. The dataset must span:

- Exact keyword lookups.

- Conceptual semantic inquiries.

- Code syntax and function signature references.

- Hierarchical multi-heading topical questions.

- Multi-Modality Evaluation Runner: Implement an automated benchmark script that evaluates the ground-truth queries across four operational modes:

- Pure Lexical Search (FTS5 BM25 alone).

- Pure Dense Vector Search (Cosine similarity alone).

- Hybrid Search (RRF fused results without reranking).

- Full Pipeline (Two-stage hybrid with cross-encoder reranking).

- Metric Calculation: Compute and report standard information retrieval metrics:

- Mean Reciprocal Rank (MRR@5): Evaluates the average rank of the first relevant chunk within the top 5 results.

- Hit@1: Measures the percentage of queries where the top-ranked chunk is an exact ground-truth match.

- Latency SLA Verification: Automatically measure and enforce per-component latency budgets:

- FTS5 Keyword Search: < 5 ms.

- FastEmbed Dense Retrieval: < 15 ms.

- Cross-Encoder Rerank (20 candidates): < 45 ms.

- Total Round-Trip Query Time: < 75 ms (p95 < 100 ms).

- CI Integration: Incorporate the benchmark runner into GitHub Actions CI (.github/workflows/ci.yml) as a blocking quality gate.

#### Acceptance & Verification Criteria

- The evaluation runner executes all 25 benchmark queries and generates structured accuracy and latency reports.

- The full hybrid + cross-encoder pipeline demonstrates measurable MRR@5 improvements over standalone BM25 and vector baselines.

- Query latency conforms to the sub-75ms average target.

- CI pipeline runs the test suite and benchmark gate automatically on pull requests and commits.

### Phase 5: Automated Storage Maintenance & Operational Runbooks

#### Objective & Scope

Prevent database fragmentation, index bloat, and storage degradation over extended operational lifecycles through automated compaction and formal operational procedures.

#### Architectural Components & Responsibilities

- Database Compaction Primitives: Implement maintenance routines in the storage layer:

- Incremental Vacuuming: Execute PRAGMA incremental_vacuum; to reclaim unused storage pages resulting from deleted or updated chunks without locking the database.

- FTS5 Index Optimization: Execute INSERT INTO chunks_fts(chunks_fts) VALUES('optimize'); to merge fragmented b-tree index segments into a single balanced index structure.

- Integrity Diagnostics: Execute PRAGMA integrity_check; and PRAGMA foreign_key_check; to verify structural health.

- Administrative MCP Primitives: Expose a maintenance tool via the FastMCP server (e.g., optimize_database) allowing client-driven or script-driven optimization.

- Automated Systemd Maintenance Timer:

- Create a systemd timer unit (~/.config/systemd/user/mcp-rag-maintenance.timer) scheduled to trigger weekly during off-peak hours.

- Bind the timer to a corresponding one-shot service unit executing the CLI maintenance command.

- Disaster Recovery & Operational Runbooks: Document clear procedures for:

- Full index rebuilds (--reindex-all) in the event of database corruption or model migrations.

- Database backups and restoration workflows.

- Model cache eviction and pre-warming routines.

#### Acceptance & Verification Criteria

- Database optimization commands execute cleanly without lock contention or data loss.

- Systemd maintenance timer activates on schedule and logs successful execution to journald.

- Triggering a full reindex cleanly purges obsolete entries and reconstructs all indices accurately.

- Integrity checks verify zero corruption after simulated high-frequency write cycles.
